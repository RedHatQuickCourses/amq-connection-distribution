Creating TLS secrets for secure broker communication

Creating TLS Secrets for Secure Broker Communication

To ensure secure communication between AMQ Broker instances and their clients, you must implement Transport Layer Security (TLS). This process involves generating cryptographic assets and storing them as Kubernetes/OpenShift Secrets so the AMQ Broker operator can mount them during pod initialization.

Overview of TLS Requirements

In a production-grade AMQ Broker environment, you typically require: * KeyStore: Contains the broker’s private key and public certificate for identity verification. * TrustStore: Contains the Certificate Authority (CA) certificates that the broker trusts when validating incoming connections.

For two-way TLS (Mutual TLS), both the client and the broker must present certificates that the other trusts.

Step-by-Step: Generating Certificates and Secrets

Follow these steps to generate the required certificates using keytool and package them into a Kubernetes Secret.

1. Generate Certificates

Use the Java keytool utility to generate the necessary stores. Ensure you replace password with a strong, secure passphrase.

# Create the Broker KeyStore
keytool -genkeypair -alias broker -keyalg RSA -keysize 2048 \
  -keystore broker.ks -storepass password -keypass password \
  -dname "CN=broker-prod-ss-0, OU=AMQ, O=RedHat, L=Raleigh, C=US"

# Extract the certificate to import into the TrustStore
keytool -exportcert -alias broker -file broker.crt \
  -keystore broker.ks -storepass password

# Create the TrustStore and import the broker certificate
keytool -importcert -alias broker -file broker.crt \
  -keystore client.ts -storepass password -noprompt

2. Create Kubernetes Secrets

Once the .ks (KeyStore) and .ts (TrustStore) files are generated, create the Kubernetes secrets. The AMQ Broker operator expects these files to be available under a specific secret name to mount them into the container.

# Create the secret for the broker KeyStore
oc create secret generic ex-aao-amqp-secret \
  --from-file=broker.ks=broker.ks

# Create the secret for the client TrustStore
oc create secret generic ex-aao-amqpsecret \
  --from-file=client.ts=client.ts

3. Verify Secret Deployment

After creation, verify that the secrets exist in your namespace:

oc get secret ex-aao-amqp-secret -o yaml
oc get secret ex-aao-amqpsecret -o yaml

Configuring the Broker for TLS

To leverage these secrets, your ActiveMQArtemis custom resource (CR) must reference these secrets in the spec section. The broker will mount these secrets into /amq/extra/secrets/.

spec:
  deploymentPlan:
    image: registry.redhat.io/amq7/amq-broker-rhel8:7.11.6
  acceptors:
  - name: amqp-tls
    port: 5671
    sslEnabled: true
    keyStoreSecret:
      name: ex-aao-amqp-secret
    trustStoreSecret:
      name: ex-aao-amqpsecret

Troubleshooting Guidance

  • Certificate Pathing: Ensure the paths defined in your AMQP connection strings or broker configuration match the standard mount point: /amq/extra/secrets/<secret-name>/.

  • Permissions: If the broker fails to start with a Permission Denied error, verify that the ServiceAccount associated with the AMQ Broker pod has permissions to read the secrets.

  • Password Mismatch: A common cause for SSLHandshakeException is a mismatch between the -storepass used during keytool generation and the configuration provided to the broker. Always use the same password for the keyStorePassword property in your connection URI.
