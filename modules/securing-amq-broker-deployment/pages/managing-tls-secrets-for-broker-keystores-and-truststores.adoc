#  Managing TLS secrets for broker keystores and truststores

= Managing TLS secrets for broker keystores and truststores

To ensure secure communication between AMQ Broker clients and the broker itself, you must implement Transport Layer Security (TLS). In a containerized environment like OpenShift, TLS certificates, keystores, and truststores are typically managed as Kubernetes Secrets.

== Understanding TLS Components

*   **Keystore:** Contains the broker's private key and public certificate, allowing the broker to identify itself to clients.
*   **Truststore:** Contains the public certificates of trusted Certificate Authorities (CAs). The broker uses this to verify the identity of incoming client connections.

== Hands-on Activity: Creating TLS Secrets

This activity demonstrates how to prepare the necessary Java Keystore (JKS) files and inject them into an OpenShift Secret for use by the AMQ Broker.

=== Prerequisites
Ensure you have `oc` (the OpenShift CLI) installed and are logged into your target cluster.

=== Step 1: Download Required Keystore Files
For this demonstration, we will use standard Apache ActiveMQ Artemis test resources to generate the keystore and truststore files.

[source,bash]
----
# Download the keystore and truststores
wget -O server-keystore.jks https://github.com/apache/activemqartemis/raw/main/tests/security-resources/server-keystore.jks
wget -O server-ca-truststore.jks https://github.com/apache/activemqartemis/raw/main/tests/security-resources/server-ca-truststore.jks
wget -O client-ca-truststore.jks https://github.com/apache/activemqartemis/raw/main/tests/security-resources/client-ca-truststore.jks
----

=== Step 2: Create the Kubernetes Secret
Use the `oc create secret` command to package these files along with their respective passwords into a single Kubernetes Secret. This object will be mounted to the AMQ Broker container at runtime.

[source,bash]
----
oc create secret generic ext-acceptor-ssl-secret \
  --from-file=broker.ks=server-keystore.jks \
  --from-file=client.ts=client-ca-truststore.jks \
  --from-literal=keyStorePassword=securepass \
  --from-literal=trustStorePassword=securepass
----

[NOTE]
====
In a production environment, ensure that `keyStorePassword` and `trustStorePassword` align with your organization's security policies. Using `--from-literal` is convenient for testing, but consider using Kubernetes Sealed Secrets for production deployments to avoid storing plain-text passwords in source control.
====

=== Step 3: Verifying the Secret
Verify that the secret was created successfully by inspecting the resources within the secret:

[source,bash]
----
oc get secret ext-acceptor-ssl-secret -o yaml
----

The output should confirm the presence of `broker.ks`, `client.ts`, `keyStorePassword`, and `trustStorePassword`. You can now reference this secret in your `ActiveMQArtemis` CR (Custom Resource) definition to secure your acceptors.

== Troubleshooting Tips
*   **Mount Path Errors:** When configuring your Broker CR, ensure the `secretName` matches exactly what you created. The AMQ Operator typically expects these files to be available under `/amq/extra/secrets/<secret-name>/`.
*   **Alias Mismatch:** If the broker fails to start, verify that the alias inside the `server-keystore.jks` matches the expected internal alias used by the broker configuration.
*   **Connection Refused:** If using two-way TLS, ensure the client is pointing to the correct `trustStorePath` and `keyStorePath` as defined in your connection URI parameters.
