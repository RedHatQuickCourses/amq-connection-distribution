#  Managing bearer tokens and direct access credentials

= Managing Bearer Tokens and Direct Access Credentials

When integrating Red Hat AMQ Broker with Keycloak, the broker utilizes Java Authentication and Authorization Service (JAAS) login modules to delegate authentication to the Keycloak server. Understanding the distinction between **Bearer Token** authentication and **Direct Access** credentials is vital for securing broker traffic and management interfaces.

== Bearer Token Authentication

Bearer token authentication is primarily used for service-to-service communication where a client already possesses a valid JSON Web Token (JWT) issued by Keycloak. The `BearerTokenLoginModule` verifies the signature and validity of the token presented by the client.

=== Configuration Requirements
To implement bearer token authentication, you must provide a `keycloak-bearer-token.json` configuration file. This file informs the login module where to find the Keycloak realm and how to validate incoming tokens.

[source,json]
----
{
  "realm": "amq-broker-realm",
  "auth-server-url": "https://keycloak-sso.apps.com",
  "ssl-required": "all",
  "resource": "amq-broker",
  "public-client": true
}
----

== Direct Access Credentials

Direct Access Grants are used when a client (such as a legacy application or an administrative script) needs to exchange a username and password directly for an access token via the Keycloak Token Endpoint. The `DirectAccessGrantsLoginModule` handles this exchange.

=== Configuration Requirements
Direct access requires a client secret to authenticate the broker instance itself with Keycloak. This is defined in the `keycloak-direct-access.json` file.

[source,json]
----
{
  "realm": "amq-broker-realm",
  "auth-server-url": "https://keycloak-sso.apps.com",
  "ssl-required": "all",
  "credentials": {
    "secret": "amq-broker-secret-value"
  },
  "resource": "amq-broker",
  "enable-basic-auth": true
}
----

== JAAS Login Module Integration

To integrate both methods, the `login.config` file used by the AMQ Broker must define the login modules. The order of these modules dictates the authentication strategy (e.g., using `sufficient` flags to allow either method).

.Example JAAS Configuration (`login.config`)
[source,text]
----
activemq {
    org.keycloak.adapters.jaas.BearerTokenLoginModule sufficient
        keycloak-config-file="${secret.mount}/_keycloak-bearer-token.json"
        role-principalclass=org.apache.activemq.artemis.spi.core.security.jaas.RolePrincipal;

    org.keycloak.adapters.jaas.DirectAccessGrantsLoginModule sufficient
        keycloak-config-file="${secret.mount}/_keycloak-direct-access.json"
        role-principalclass=org.apache.activemq.artemis.spi.core.security.jaas.RolePrincipal;
};
----

== Hands-on Lab: Provisioning Secrets

Before the broker can utilize these configurations, they must be mounted into the pod via a Kubernetes/OpenShift secret.

=== Step 1: Create the Secret
Use the `oc create secret` command to bundle the configuration files into a single object. This secret will be mounted to the directory referenced by `${secret.mount}` in your deployment.

[source,bash]
----
oc create secret -n amq generic keycloak-jaas-config \
  --from-file=login.config \
  --from-file=_keycloak-bearer-token.json \
  --from-file=_keycloak-direct-access.json
----

=== Step 2: Verification
Ensure the secret is correctly populated in your namespace:

[source,bash]
----
oc get secret keycloak-jaas-config -n amq -o yaml
----

[TIP]
====
When managing these credentials in production, ensure the `amq-broker-secret-value` is never stored in plain text in your version control system. Use OpenShift native secret management or a Vault integration.
====
