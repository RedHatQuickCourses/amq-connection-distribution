#  Manage TLS certificates and keystore secrets for HTTPS console access

= Manage TLS certificates and keystore secrets for HTTPS console access

To secure the AMQ Broker management console, you must configure Transport Layer Security (TLS). This ensures that traffic between the client and the broker console is encrypted, preventing unauthorized access to administrative functions.

== Conceptual Overview

AMQ Broker uses Java KeyStores (JKS) to manage cryptographic keys and certificates. To enable HTTPS access for the console:
1.  **Keystores and Truststores:** You must generate or obtain a server keystore (containing the private key and public certificate) and a truststore (containing the Certificate Authority (CA) certificates).
2.  **Kubernetes Secrets:** These files must be mounted into the broker pod as Kubernetes secrets so the broker application can access them during startup.
3.  **Mounting Configuration:** The AMQ Broker custom resource must reference these secrets to enable the TLS listener on the console port.

== Hands-on Lab: Provisioning TLS Secrets

In this activity, you will prepare the necessary certificates and create the Kubernetes secrets required for secure HTTPS console access.

=== Step 1: Prepare the Keystore and Truststore
For this exercise, we will download pre-existing test certificates provided by the Apache ActiveMQ Artemis project.

[source,bash]
----
# Download test keystores and truststores
wget -O server-keystore.jks https://github.com/apache/activemqartemis/raw/main/tests/security-resources/server-keystore.jks
wget -O client-ca-truststore.jks https://github.com/apache/activemqartemis/raw/main/tests/security-resources/client-ca-truststore.jks
----

=== Step 2: Create the Kubernetes Secret
Create a generic secret named `mytlssecret`. The broker operator expects the files to be provided with specific keys that map to the internal keystore configuration.

[source,bash]
----
oc create secret generic mytlssecret \
  --from-file=broker.ks=server-keystore.jks \
  --from-file=client.ts=client-ca-truststore.jks \
  --from-literal=keyStorePassword=securepass \
  --from-literal=trustStorePassword=securepass
----

[NOTE]
====
Ensure the secret name matches the one defined in your `ActiveMQArtemis` custom resource specification. If you change the secret name, you must update the broker deployment manifest accordingly.
====

=== Step 3: Configure the AMQ Broker Custom Resource
To enable HTTPS for the console, you must reference the secret in your `ActiveMQArtemis` CR. Update your deployment YAML file to include the secret:

[source,yaml]
----
spec:
  console:
    enabled: true
    sslSecret: mytlssecret
----

=== Troubleshooting Guidance
*   **Secret Not Found:** Ensure the secret is created in the same namespace as the AMQ Broker instance. Use `oc get secret mytlssecret -n <namespace>` to verify existence.
*   **Handshake Failures:** If you encounter SSL handshake errors when accessing the console, ensure the `keyStorePassword` and `trustStorePassword` match exactly what was used when creating the secret.
*   **Certificate Validity:** If using self-signed certificates, ensure your browser is configured to trust the CA that signed the certificate, or you will receive a "Connection not private" warning in the browser.
